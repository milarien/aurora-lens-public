# Aurora-Lens Evidence Model

This document describes what the aurora-lens audit infrastructure produces, what
each component of the audit record means, how to verify it, and what the system
does and does not prove.

It is intended for: operators, security reviewers, legal counsel, and any third
party who receives an exported audit log as part of an incident or compliance review.

---

## 1. Audit record fields

Every audit entry is a single line of JSON (JSONL). The following fields appear
in entries produced by the canonical bridge paths.

### Core envelope fields

| Field | Type | What it means |
|---|---|---|
| `schema_version` | integer | Record schema version (currently `2`). |
| `run_id` | string (UUID4) | Identifies the specific proxy process instance that wrote this entry. Stable for the lifetime of the process; changes on restart. Allows attribution of entries to a specific deployment instance. |
| `trace_id` | string | Request-scoped correlation identifier. All entries from one HTTP request share a `trace_id`. |
| `timestamp` | string (ISO-8601 UTC) | Time the entry was written, with microsecond precision and `+00:00` suffix. Example: `2026-02-26T10:00:00.123456+00:00`. |
| `session_id` | string or null | Conversation session identifier (set by the caller or generated by the proxy). |
| `turn` | integer | Conversation turn index within the session. |
| `outcome` | string | Governance action taken: `PASS`, `SOFT_CORRECT`, `CONTAIN`, `FORCE_REVISE`, or `HARD_STOP`. |
| `failed_constraints` | array of strings | Flag types that triggered a non-PASS outcome. |
| `original_response` | string or null | The raw LLM response text before any governance intervention. |
| `state_hash` | string | SHA-256 hex digest of the PEF context string at decision time. Used for state-replay verification. |

### PEF snapshot and linkage (posture)

| Field | Type | What it means |
|---|---|---|
| `pef_snapshot` | object or null | Serialized `PEFState` **after** this decision (durable world-state at the audit boundary). When paired with `forensic_event.state_hash`, state-hash replay recomputes the hash from this object. |
| `pef_turn_classification` | string or null | Turn-entry posture recorded for this row: `fresh`, `held_ambiguity`, `held_refusal`, or `stopped`. Absent on legacy logs. |
| `pef_hold_transition` | string or null | Posture delta at this decision boundary: `none`, `ambiguity`, `refusal`, `stop`, `supersede`, `release`. |

**Operator note:** `pef_turn_classification` describes **governing epistemic posture** (what durable hold or clarification is in force), not the raw `InterventionAction` name. See `aurora_lens/pef/audit_linkage.py`.

### Tamper-evident ledger fields (hash chain / HMAC)

These fields prove **integrity of the log as stored**: append order, absence of silent edits, and (when configured) possession of the signing key. They do not by themselves prove **what software build or policy configuration** produced a row.

| Field | Type | What it means |
|---|---|---|
| `cid` | string | Content identifier for this entry. SHA-256 hash of the canonical JSON of the entry (excluding `cid`, `prev_cid`, `hmac`), combined with `prev_cid`. Provides cryptographic linkage to the preceding entry. |
| `prev_cid` | string | CID of the immediately preceding entry, or `"genesis"` for the first entry. Together, `cid` and `prev_cid` form a hash chain: any deletion, insertion, or reorder of entries breaks the chain. |
| `hmac` | string (hex) | HMAC-SHA256 of the canonical JSON of the entry (after `cid`/`prev_cid` are set, before `hmac`). Computed over all fields with `sort_keys=True, separators=(",", ":")`. Proves the entry was written by a party with access to the signing key. |

### Evidentiary packaging (`chain_of_custody`)

**Distinct from** the tamper-evident chain above: a structured **chain-of-custody** object on each row records **code, policy/config, and runtime provenance** so an exported package can be tied to a reproducible deployment context. Rows may carry `evidence_audit_status: "degraded"` when required runtime attribution (e.g. model/provider) is missing—this is explicit on the artifact, not a silent downgrade.

| Field / path | Type | What it means |
|---|---|---|
| `chain_of_custody.chain_of_custody_version` | string | Format version of the block (currently `1.0`). |
| `chain_of_custody.evidence_audit_status` | string | `complete` or `degraded` (must align with `evidence_degradation_reasons`). |
| `chain_of_custody.evidence_degradation_reasons` | array of strings | Empty when `complete`; when `degraded`, non-empty (e.g. `runtime_model_provenance_incomplete` if `AURORA_MODEL_ID` / `AURORA_PROVIDER` are unset). |
| `chain_of_custody.code.application_version` | string | Aurora-Lens package version (from installed distribution or `__init__.py`). |
| `chain_of_custody.code.git_commit` | string or null | Git HEAD when resolvable, or `AURORA_GIT_COMMIT`. |
| `chain_of_custody.code.git_working_tree_clean` | bool or null | Whether the tree was clean, or `AURORA_GIT_DIRTY` override. |
| `chain_of_custody.code.git_commit_source` | string | `git`, `env`, or `unavailable`. |
| `chain_of_custody.policy.policy_version` | string or null | Governor matrix / policy version (canonical bridge) or built-in policy label. |
| `chain_of_custody.policy.policy_source` | string or null | Resolver source string when applicable. |
| `chain_of_custody.policy.governance_config_fingerprint` | string | `sha256:` hash of canonical JSON of governance-relevant config (see `_governance_config_snapshot`). |
| `chain_of_custody._governance_config_snapshot` | object | Same bytes as hashed for the fingerprint (for offline replay). |
| `chain_of_custody.runtime.hostname` | string | Process hostname. |
| `chain_of_custody.runtime.service_instance_id` | string | `AURORA_SERVICE_INSTANCE_ID` or hostname fallback. |
| `chain_of_custody.runtime.model_id` | string or null | `AURORA_MODEL_ID` when set. |
| `chain_of_custody.runtime.provider` | string or null | `AURORA_PROVIDER` when set. |

When `forensic_event` is present, `chain_of_custody` is also copied under `forensic_event.chain_of_custody` and included in `event_hash`.

### Evidence status fields — three distinct fields, do not conflate

Audit rows carry **three separate "is this okay" fields**, each about a different subsystem. All three can independently be `complete`/`degraded` (or their own status vocabulary) without implying anything about the other two. Operators reading `/forensics` or a raw row must read the label, not just the color of the pill.

| Field | Values | What subsystem it describes | Set by |
|---|---|---|---|
| `chain_of_custody.evidence_audit_status` | `complete` \| `degraded` | **Packaging**: whether this row's chain-of-custody envelope (code/policy/runtime provenance block) is fully populated. Degrades when required runtime model/provider attribution is missing — see the table above. | `build_chain_of_custody_bundle()` (`aurora_lens/govern/chain_of_custody.py`) |
| `provenance_status` | `complete` \| `degraded` | **Instrument**: whether the *governing instrument* (policy/ruleset/instrument id that authorized this decision) is identified. Degrades only when `instrument_id`, `instrument_version`, and `ruleset_hash` are all absent. Unrelated to evidence capture or packaging. | `compute_provenance_status()` (`aurora_lens/govern/instrument_provenance.py`) |
| `request_capture_status` | `sealed_by_policy` \| `hash_only` \| `omitted` \| `forbidden_by_policy` (etc.) | **Capture**: what the evidence vault actually did with *this request's* content — sealed and encrypted, hashed only (no retrievable plaintext), or not captured at all. This is the field that answers "what do we actually have on file for this request." | `capture_governance_evidence()` (`aurora_lens/govern/evidence_capture.py`) |

A companion field, `evidence_capture_mode` (`sealed` \| `redacted` \| `hash_only` \| `plaintext_dev`), records the request manifest's effective protection mode (or the selected mode when no request manifest exists). Required sealed deployments reject startup for missing keys or unavailable storage and retain every available request, including strict low-risk and moderate PASS requests. PASS output-retention settings cannot downgrade sealed request capture. Diagnostic `/health` exposes deployment `evidence_capture.requested_mode` and `effective_mode` separately from these per-request receipt fields. Historical hash-only records are unchanged and do not become recoverable.

All four fields are surfaced together (with these exact labels) on the `/forensics` operator dashboard: the recent-rows table shows `evidence_audit_status` and `request_capture_status`/`evidence_capture_mode` in the "Evidence" cell, and the row detail panel labels all four explicitly ("Evidence packaging (chain-of-custody)", "Evidence capture — this request", "Evidence capture mode — configured", "Instrument provenance").

### Forensic event sub-record

Present in entries where outcome is not `PASS` or `SOFT_CORRECT`. Contains the
detailed governance decision record.

| Field | Type | What it means |
|---|---|---|
| `trace_id` | string | Same as the outer entry. Enables cross-referencing. |
| `session_id` | string or null | Conversation id when set (ContextVar / proxy); duplicated on the artifact so the envelope is correlatable if exported without the outer row. |
| `timestamp` | string (ISO-8601 UTC) | Same as the outer entry. |
| `status` | string | Governance status: `ASK`, `REFUSE`, or `STOP`. |
| `attempted_action` | string | What the system was attempting when the decision was made. |
| `failed_constraints` | array | Same as outer entry. |
| `state_hash` | string or null | SHA-256 of the PEF snapshot (full world-state). When `pef_snapshot` is also present in the outer entry, this hash can be recomputed from the snapshot for independent verification. |
| `event_hash` | string | `sha256:` prefixed SHA-256 of the canonical JSON of all other fields in the forensic_event (excluding `event_hash` itself). Allows the forensic_event to be verified in isolation, without the outer audit entry. |

### AttestedOutput (HMAC-signed record)

Produced when a `secret_key` is configured. Not written to the log file; held
in memory on the bridge instance and optionally exposed via API.

| Field | Type | What it means |
|---|---|---|
| `content` | string | The governed response content. |
| `policy_cid` | string | Content identifier for the policy profile in effect. |
| `rationale_code` | string | Governance action name. |
| `decision` | string | Same as `rationale_code`. |
| `event_cid` | string | FNV-64 CID of the governance event. |
| `signature` | string (hex) | HMAC-SHA256 over the canonical payload (`content`, `policy_cid`, `rationale_code`, `decision`, `event_cid`, `meta`). |
| `meta.timestamp` | string | UTC ISO-8601 timestamp of the decision. |
| `meta.trace_id` | string | Request trace ID. |
| `meta.session_id` | string or null | Session ID. |
| `meta.run_id` | string | Process-startup UUID. |

## 2. The two-layer evidence model

Aurora-lens produces two distinct categories of evidence.

### Layer 1: Deterministic evidence (test suite)

All tests in `tests/` that do not require a live LLM are **deterministic**. They
run against fixed inputs and produce the same output on every run. They are
reproducible by any party with the source code and a Python 3.12 environment.

These tests prove:
- The governance rules fire correctly for specific inputs.
- The audit chain links correctly across sequential decisions.
- HMAC signing and verification round-trips correctly.
- Tamper detection works for both chain breaks and HMAC failures.

See **`private/test_evidence_report.md`** when that file is present in your tree
(a full test inventory with counts). It is not shipped in all checkouts; as a
fallback, use `pytest --collect-only` from the repository root to enumerate
tests.

### Layer 2: Live-LLM evidence

Tests in `tests/test_real_llm.py` and `tests/test_ollama_llm.py` run against a
real language model. These tests are **not fully deterministic** because LLM
outputs can vary between runs.

Live-LLM tests demonstrate that the governance layer intercepts and handles
real model outputs correctly. They are run as integration smoke tests.

## 3. State hash replay procedure

The `state_hash` field in `forensic_event` allows independent verification that
the PEF snapshot embedded in the audit entry is the one that was actually used
at decision time.

**Step-by-step:**

1. Locate an audit entry that has both `forensic_event.state_hash` and
   `pef_snapshot` in the outer entry.
2. Extract `pef_snapshot` (a JSON object).
3. Compute:
   ```python
   import hashlib, json
   computed = hashlib.sha256(
       json.dumps(pef_snapshot, separators=(",", ":"), sort_keys=True).encode()
   ).hexdigest()
   ```
4. Assert `computed == forensic_event["state_hash"]`.

This is automated by the verifier CLI:
```
python -m aurora_lens.scripts.verify_audit --path audit.jsonl --key $KEY
```

Any CLI failure (HMAC, chain, replay, PEF linkage, chain-of-custody) prints **plain-language** stderr: what failed, a file line hint when possible, and an internal code for cross-reference—not a bare stack trace.

## 4. PEF turn linkage verification

When a row includes `pef_turn_classification`, an independent check can tie that token to the **previous** row’s `pef_snapshot` (the durable PEF state after the prior decision). For each consecutive pair (`prev`, `curr`), if `curr` has `pef_turn_classification` and `prev` has a JSON object `pef_snapshot`, the check requires:

`curr["pef_turn_classification"] == classify_pef_turn_start(PEFState.from_dict(prev["pef_snapshot"]))` (string value).

Rows without `pef_turn_classification` are skipped (legacy logs). Pairs where `prev` has no dict `pef_snapshot` are skipped (e.g. PASS-only rows without a forensic payload).

Implementation: `verify_pef_linkage` in `aurora_lens.govern.audit_io`. Automated tests: `tests/test_audit_pef_linkage.py`, `tests/test_verify_pef_linkage_replay.py`.

**CLI (runs with normal chain + HMAC + optional state-hash replay; add flag for linkage):**
```
python -m aurora_lens.scripts.verify_audit --path audit.jsonl --key $KEY --pef-linkage
```

## 5. Chain verification procedure

### JSONL flat chain (D2)

Each entry contains `cid` and `prev_cid`. The `cid` is computed as:
```
cid = sha256(canonical_json(entry_without_cid_and_prevCid) + ":" + prev_cid)
```

To verify:
```
python -m aurora_lens.scripts.verify_audit --path audit.jsonl --key $KEY --no-replay
```

When the proxy runs with `governance.audit_backend: jsonl` and a signing key, the same checks are available over HTTP:

```
GET /v1/audit/verify
```

The response includes `verified`, `hmac_verified`, and `chain_verified` (see operator
documentation). Use the CLI when you have filesystem access to the log alone.

Or programmatically:
```python
from aurora_lens.govern.audit_io import verify_chain
ok, entries, break_idx, reason = verify_chain("audit.jsonl", n=10000)
```

### AFL-JSONL-1 forensic ledger (ForensicLedger)

The ledger uses a SHA-256 hash chain over all entry fields (excluding `hash`,
`sig`, `root`). Each entry's `hash` field covers all other fields. `prev` points
to the preceding hash.

Verify via:
```
GET /v1/audit/verify
```
Or programmatically:
```python
from aurora_lens.govern.forensic_ledger import ForensicLedger
ledger = ForensicLedger("audit.jsonl")
ok = ledger.verify()
```

### Chain-of-custody block (evidentiary packaging)

This verifies the **provenance object** on each row (not the hash chain): fingerprint replay against the embedded governance snapshot, required subfields, and consistency of `evidence_audit_status` with `evidence_degradation_reasons`. Rows without `chain_of_custody` are skipped (legacy logs).

```
python -m aurora_lens.scripts.verify_audit --path audit.jsonl --key $KEY --chain-of-custody
```

Optional **`--require-complete-evidence`**: fail if any checked row has `evidence_audit_status: "degraded"` (e.g. missing `AURORA_MODEL_ID` / `AURORA_PROVIDER`). On failure, stderr includes a plain-language explanation, the physical line number in the file, what the row recorded (`evidence_audit_status`, degradation reasons, model/provider fields), and the internal verifier code for support cross-reference.

```python
from aurora_lens.govern.audit_io import verify_chain_of_custody_rows
ok, checked, idx, reason = verify_chain_of_custody_rows(
    "audit.jsonl", n=1000, require_complete_evidence=False
)
```

## 6. What this system does NOT prove

The following limitations must be stated explicitly.

1. **Host clock trust.** `timestamp` fields reflect the host system clock.
   If the host clock is wrong or manipulated, timestamps will be incorrect.
   The system does not use an external time source (NTP is an infrastructure
   guarantee, not a software guarantee).

2. **Host OS integrity.** If an attacker has root access to the host running
   the proxy, they can read the signing key from process memory, modify the
   audit log file, recompute the chain, and re-sign all entries. The signing
   key is a single point of failure.

3. **Extraction completeness.** The Lens extraction layer uses structural NLP
   to identify claims in LLM output. It does not guarantee that all claims are
   extracted. Unextracted claims are not verified.

4. **Legal admissibility.** This system implements engineering controls for
   audit integrity. Whether any specific audit log is admissible as evidence in
   any legal jurisdiction is a legal determination, not an engineering one.
   The system does not claim legal admissibility.

5. **LLM output correctness.** The governance layer gates LLM output against
   the PEF world-state. It does not independently verify that the PEF
   world-state is accurate.

6. **Network confidentiality.** Audit entries contain the original LLM response
   (`original_response`). If the log file is transmitted or stored unencrypted,
   this content may be exposed.

## 7. Evidence bundle format

An evidence bundle is a directory produced by `scripts/smoke_proof_bundle.py`
containing:
- `proof_bundle.txt`: Human-readable transcript of the smoke test run.
- `audit_entries_redacted.json`: Last several audit entries with sensitive
  content truncated.
- `manifest.json`: Machine-verifiable file inventory.

### manifest.json schema

```json
{
  "bundle_version": "1",
  "created_at": "<UTC ISO-8601>",
  "run_id": "<session-id-from-smoke-test>",
  "files": [
    {
      "name": "proof_bundle.txt",
      "sha256": "<hex>",
      "size_bytes": 12345
    }
  ]
}
```

**Verifying a received bundle:**
```
python scripts/verify_bundle.py ./proof_bundle/
```
Exit code 0 means all files match the manifest. Exit code 1 means tampering or
missing files were detected.

## 8. Retention recommendations

Retention period is an operator decision and must comply with applicable law and
regulatory requirements.

Engineering recommendations:
- **Minimum:** Retain audit logs for at least the duration of any live contract,
  service agreement, or regulatory obligation that depends on governed outputs.
- **Write-once/WORM storage** is the strongest integrity guarantee for long-term
  retention. The code does not require WORM, but it is recommended for
  deployments with legal or compliance obligations.
- **Key custody:** Retain the signing key that was active for each log segment.
  Without the key, HMAC verification is impossible for that segment.

## 9. Transferring evidence to a third party

When transferring an audit log to a regulator, auditor, or legal counsel:

**Architecture note (reviewers):** In some configurations, more than one subsystem
may append ledger or JSONL rows for a single governance episode. Consecutive lines
can share a `trace_id`. Use `turn`, `cid` / `prev_cid`, schema fields, and row
`outcome` rather than assuming strictly one line per HTTP request.

1. **Export the log with a custody record:**
   ```
   python scripts/export_log.py --log audit.jsonl --exported-by "Your Org" --output custody.json
   ```
   This produces a custody record JSON with the file's SHA-256, size,
   non-empty line count, export timestamp (UTC), and optional `exported_by`
   label (`AURORA_LENS_EXPORTED_BY` or `--exported-by`; `--operator` is an alias).

2. **Record the signing key** (or the key rotation history) so the recipient
   can independently verify HMAC signatures. Transmit the key via a separate
   secure channel from the log file.

3. **One governance row per decision:** On the scanner gate / AFL ledger path,
   `intervene()` does not append audit lines. The canonical `forensic_event` is
   built with `build_forensic_event`, enriched for Governor vocabulary (canonical
   bridge), hash-refreshed, then written once inside the `log_decision()` ledger
   append (`op` matches the intervention action). Two lines with the same
   `trace_id` still occur for unrelated reasons (e.g. subsystem events); use
   `op` and `seq` to interpret the chain.

   **Flat JSONL vs AFL outer format:** When `AuroraScannerGateBridge` /
   `CanonicalScannerGateBridge` uses `backend="jsonl"`, the outer row is schema v2
   flat JSONL (D2 chain, `outcome`, etc.) instead of an AFL envelope. The
   **same** forensic pipeline applies: `_prepare_governance_forensic_event` computes
   the FNV CID, calls `build_forensic_event(..., audit_id=cid)`, then
   `_postprocess_forensic_event` (Governor enrichment and `event_hash` refresh on
   the canonical bridge) before the row is serialized. Only the transport differs;
   the embedded `forensic_event` contract matches the ledger path.

4. **Verify before transfer:**
   ```
   python -m aurora_lens.scripts.verify_audit --path audit.jsonl --key $KEY
   ```
   Include the verifier output in the custody record.
