# Translation-assisted admission: bounded candidate stage

## Work stopped by user instruction — 2026-10-12

Translation development is stopped. Retain the other verified governance repairs and the existing candidate containment behavior; this instruction does not remove the fidelity gate or enable translated admission. No further translation implementation or architectural expansion is planned under the current task.

The subsequently authorised [language-support admission task](language-support-admission.md) is separate. Its boundary assessment does not resume translation development or establish translation fidelity. The language-gap description below records the deployed state before that separate boundary is verified and released.

The supported governance scope remains English-only. The implemented translation stage can retain a source-linked, untrusted English candidate, but cannot establish its fidelity or admit it as the source request. Detected unsupported input remains held and requires an English restatement, which is assessed as new user evidence under normal governance. Restatement does not automatically clear earlier holds or authorise their requested consequences.

There is also an open input-admission limitation: unsupported Latin-script or mixed-language input can miss the existing interpretation-limit triggers and reach ordinary English processing, including state admission. The public demo supplies no `translation_required` flag. Therefore unsupported input is not guaranteed to be detected or contained. Candidate containment does not close this gap, and no general multilingual governance or completed translate-then-adjudicate capability is claimed.

The architectural decisions described below are historical outstanding capability requirements, not authorised next steps. Resuming this work would require a new instruction and an explicit fidelity-evidence and input-capability contract.

This repair implements a quarantined transformation stage, not general multilingual governance or automatic translated admission. Lens remains English-only. An English parser result and a fluent translator output are not language or fidelity evidence.

## Entry points

The production proxy enables candidate assistance for input already held by the interpreter as UNSUPPORTED_SCRIPT or MAIN_ACT_UNDETERMINED. Those are existing interpretation limitations, not language identification. A caller can explicitly request the same restrictive path with `request_metadata: {"translation_required": true}`. This supplies a manual entry point for caller-flagged Latin-script and mixed-language input; it does not identify their language. No accent, punctuation, dictionary, parser-success, or model-confidence language heuristic supplies that signal. The metadata is an opt-in to containment and transformation; it is not a language claim, verified authority, fidelity attestation, or admission permit. A programmatic Lens enables automatic candidates with `LensConfig.enable_translation_candidates`; default false preserves existing integrations. Proxy opt-out: AURORA_LENS_TRANSLATION_CANDIDATES=0, which leaves existing containment intact. Explicit metadata still requests candidate assistance.

Some unsupported Latin-script input produces no existing interpretation limit. For example, `Shortlist applicants si son mayores de 50.` and `Ella no aprobo eso si faltaban dos firmas.` can parse without one. Without explicit metadata there is no reliable automatic translation-needed detector. This repair does not pretend to close that capability gap. Applying candidate assistance to every input, or admitting a language classifier as authoritative, would require a substantive capability contract beyond the current architecture.

## State and call boundaries

Before the call, preserve the original text in a pending interpretation hold without replacing a separate prior matter. Append a typed TranslationCandidate outside entities, relationships, bindings and ordinary prompt world context. Link source and candidate by source_text, source SHA-256, candidate SHA-256, turn and adapter model. Original text is never overwritten. Both pre-call and post-call audit rows identify transformation_attempt/call_purpose=translation_only. Calls, failure, model and fidelity status are explicit. Operator telemetry reports translation_calls separately from answer_generation_called; a translator output is not an answer-generation candidate.

Use the existing transport adapter in an isolated two-message translation-only request: no conversation history, no PEF world context, no answer prompt, tools or action-execution path. Source text is a JSON string treated as untrusted data. The fixed system instruction requires preserving actors, negation, quantities, dates, conditions, references and ambiguity and translating embedded instructions instead of obeying them. Candidate output must have the exact source echo, english_text, and unresolved_items schema. Schema and echo checks establish linkage only, never semantic fidelity. Even a schema-valid answer, changed negation, invented approval, confident translation, or silently resolved reference remains untrusted and held.

One call per turn, 30-second timeout, 16 KiB source and 32 KiB response bounds. Oversize, malformed, empty, provider-error and timeout cases fail closed with typed failure; raw provider errors are not stored. No candidate tokens stream to the client. The existing streaming early-result handler releases only the governance clarification. Translation reuses the adapter and bounded-attempt discipline; the existing Governor revision handler is a deterministic answer intervention, not a bilingual verifier, and is not used to launder source text into an answer revision.

## Admission and continuation

Existing source-side blocked-request checks and final refusal gates retain their authority. Quarantined candidates receive existing blocked-request, financial-probe and semantic-transaction checks on a deep copy of PEF. Findings are explicitly candidate_policy_flags, not established findings about the source. No candidate reaches update_pef, binding resolution, reset control, answer generation or consequence release. Prior holds and reset disposition records survive; source control words are data when translation_required is set.

No independent bilingual fidelity verifier exists in this architecture. Therefore fidelity remains unestablished; the original request stays CONTAIN and the user is asked to restate it in English with all unresolved information preserved. An English restatement is new user evidence and receives normal Lens policy/admission checks. It is not translator verification and does not automatically discharge the original hold or authorise a held exclusion/approval. No automatic candidate-to-admitted-request transition is supplied. A future admissible fidelity basis requires an explicit verifier contract covering actors, polarity, quantities, temporal/conditional scope and unresolved references; translator confidence, round-trip resemblance and parser fluency cannot supply that contract.

## Verification scope

Recovered Hindi T12h/T05h and Spanish T05c originals are distinguished from reconstructed controls. Tests cover accent-free Spanish, mixed language, negation, dates/conditions/quantities, ambiguous references, embedded translator redirection, schema-valid altered candidates, malformed/provider failure, English controls, prior T13/approval holds, reset-as-source data, final refusal, normal English restatement, serialization and audit/telemetry in normal and stream-requested paths. Live records and exact commits are maintained in the local reports rather than published runtime diagnostics.

## Exact remaining transition and design decision

`Lens._translation_candidate_hold` unconditionally creates the `TRANSLATION_FIDELITY_UNESTABLISHED` interpretation constraint before calling the translator. A valid candidate sets `status=candidate_unverified`; `TranslationCandidate.fidelity` remains `unestablished` and deserialization cannot upgrade it. The candidate receives only provisional request-policy and semantic-transaction observations on a copied PEF. There is no fidelity-evidence validator, accepted-fidelity state transition, or candidate-to-normal-Lens handoff. The helper returns the held response instead of entering answer generation or `update_pef`. This is an unfinished translate-then-adjudicate capability, not a completed repair achieved by permanent quarantine.

Fidelity asks whether this English text preserves the original actors, negation, quantities, dates, conditions, references and unresolvedness. English adjudication asks whether that interpretation is admissible under Lens policy and state constraints. Employment flags on an English candidate answer only the latter question provisionally; they do not establish what the original meant. A policy PASS or CONTAIN is equally incapable of establishing fidelity.

The existing architecture can accept explicit English user restatement and referent/criterion clarification as new user-input evidence, subject to the normal interpretation, authority, refusal and admission checks. That does not certify the candidate as a faithful translation of the earlier source, discharge another hold, or authorise an exclusion. Source hashes, schema/source echoes, audit evidence and registered-source trust establish linkage or source properties; their contracts contain no bilingual-equivalence proof. The corpus intake translator produces establishment-failure proposals, not language verification. No currently accepted evidence object grants translation fidelity.

The remaining substantive decision is which independent, authorised fidelity-evidence contract Lens should accept, who may supply it, how it preserves the listed semantic slots and unresolvedness, and how failed or conflicting attestations remain held. That contract and its explicit admission transition must exist before normal adjudication can consume a candidate as an interpretation of the source. Translator confidence, a second uncontracted model opinion, back-translation resemblance, parser success, or user permission to proceed cannot silently replace it.

## Public-demo admission gap

`aurora_lens/proxy/demo.html:buildChatRequestBody` sends model, messages, session ID and (for selected workflows) execution-task fields. It supplies neither `request_metadata` nor `translation_required`; there is no demo language selector supplying it. API callers supply that optional Boolean, and diagnostic runs set it for their explicitly labelled reconstructed cases. Automatic entry is supplied only by the existing interpreter limitation kinds. When an unsupported input produces neither limitation and the caller does not set the flag, normal English interpretation, answer generation and state admission remain reachable. This is an open admission gap, separate from missing fidelity verification. A reliable language/capability admission contract or an explicit product input boundary is needed; adding a flag to selected diagnostics does not close the public-demo gap.
